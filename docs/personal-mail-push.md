# 个人邮件推送

自 `v1.1.0` 起，Cloud Mail Plus 同时支持两套互相独立的收件推送：

- **全域推送**：保留在“系统设置 → 邮件推送”，仅管理员可配置，继续作用于整个站点的收件邮件。
- **个人推送**：位于“个人设置 → 个人邮件推送”，管理员和普通用户都可配置，但只处理当前用户自己名下邮箱收到的邮件。

## 可配置项目

每个用户都可以独立配置：

- Telegram Bot Token；
- 一个或多个 Telegram Chat ID；
- Telegram 消息中的发件人、收件人和正文显示方式；
- 一个或多个第三方转发邮箱；
- “全部转发”或仅推送指定自有邮箱。

Telegram Bot Token 只保存在 Worker 后端的 D1 数据库中。查询个人设置时，前端只能看到“是否已配置”，不能读回 Token。第三方转发邮箱必须先在 Cloudflare Email Routing 中验证。

## 用户与邮件隔离

个人配置以 `user_id` 为主键保存。Worker 收到邮件后先确定实际收件邮箱所属用户，再读取该用户的个人配置。因此：

- 用户不能读取或修改其他用户的推送配置；
- 规则模式只接受当前用户有效邮箱列表中的地址，服务端会再次校验；
- `name+tag@example.com` 等加号地址按照其所属的基础邮箱 `name@example.com` 应用个人规则；
- 无本地归属、已删除邮箱、已删除用户或已停用用户不会触发个人推送；
- 删除用户的物理数据时会同步删除该用户的个人推送配置。

全域和个人规则分别判断。两者可以同时生效；如果配置了相同的 Telegram Chat ID 或相同转发邮箱，同一封邮件可能产生两次通知，这是预期行为。

## 升级和初始化

部署新版本后必须再次执行数据库初始化。GitHub Actions 自动部署流程会调用受保护的 `POST /api/init`，手动部署则应按现有部署文档完成初始化。初始化会幂等创建：

```sql
CREATE TABLE IF NOT EXISTS user_push_setting (...);
```

这不会修改既有用户、邮箱、邮件、SSO 身份绑定或系统级推送配置。所有用户的个人推送默认关闭，只有用户主动保存并启用后才会工作。

## 验证建议

1. 用普通用户登录，确认“个人设置”中出现“个人邮件推送”。
2. 配置该用户自己的 Telegram Bot/Chat ID 或已验证的转发邮箱并启用。
3. 向该用户邮箱发送测试邮件，确认个人目标收到通知。
4. 向另一个用户邮箱发送测试邮件，确认第一个用户的个人目标没有收到通知。
5. 启用管理员全域推送，再次测试，确认全域目标与邮件所属用户的个人目标均能收到通知。
6. 将个人规则切换为指定邮箱，确认用户不能提交其他用户的邮箱。

路由与输入校验有单元测试覆盖；前端构建和 Worker 上传包也应在发布前通过 CI。
